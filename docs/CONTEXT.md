# 项目背景与会话上下文

## 用户真正想解决的问题

用户玩 WoW Forever，希望直接向 AI 询问“现在该做哪些任务、哪些可以放弃、附近有哪些目标、装备是否合适”，而不必手工粘贴任务日志、截图或上传文件。先让 AI 能准确获得角色上下文，再讨论任务建议本身。

需求最初来自作者的一次 AI 聊天（任务取舍建议）。本文件只整理与工程有关的内容，不复制聊天原文，也不把早期助手的猜测视为事实。

用户明确表达过：

- “不想手动”，不要自己复制粘贴。
- 优先“最快最快”的最小可行方案。
- “不需要做 UI”，运行一个脚本即可输出信息。
- 要实际试用，不能只停留在研究或架构图。
- 后续要在不同电脑、不同 chat/session 继续，因此需要代码和足够的 Markdown 上下文一起进入 GitHub。

## 范围如何收敛

初期讨论过 SavedVariables 导出、ForeverSync、本地 Agent 和 MCP。用户随后将范围收敛为 MVP 0：游戏插件加本地读者，自动产生 `player.json`，先由本地 Codex读取。首轮不需要 MCP、网站、数据库或 UI。

2026-11-27 第二次会话，用户扩大目标：让 ChatGPT 或 Claude 等 AI 读取最新角色信息，回答“下一步做什么”；轻量、本地存储。讨论后决定（D12）：不上云、不同步、不做隧道，由游戏电脑上的桌面客户端通过本地只读 MCP 读取。用户有 ChatGPT Plus 和 Claude Pro，倾向包月订阅而非按 token 计费。

最初认为可复用 ForeverSync 全部输出；审阅源码后发现其任务文本和已穿装备覆盖不足，于是选择独立的小插件。不是因为无法找到真实 Windows，而是在实际访问机器后做出的实现取舍。

## 已确认的产品约束

| 项目 | 约束 |
| --- | --- |
| 采集 | 仅受支持的游戏 API 和本地日志；不访问游戏内存 |
| 操作 | 不模拟键鼠、不自动打怪、不自动做任务 |
| 使用 | 一次启动，自动输出；首次加载新插件可正常重启游戏 |
| 数据 | 中文名原样保留，所有未知或不可用状态明确标注 |
| 架构 | Local First，无云数据库、无公网服务、无云盘同步；本地只读 MCP 已获批准（D1、D12） |
| 验证 | 必须区分模拟、历史真实数据、实时端到端验证 |
| GitHub | 私有仓库，保存代码/设计/进度；不上传原始聊天日志 |

## 现场经过与已纠正判断

2026-11-26 在游戏电脑上找到 `_forever_` 安装目录。最初受限环境的进程枚举没有显示 WoW，后来在实际 Windows 会话发现游戏一直在运行。不能再引用“没有运行游戏”作为事实。

安装插件时客户端已启动，因此新插件需要正常退出重开。2026-11-27 用户让我们重试时，游戏已开始写 LCB1 数据，但上一次后台读者已停止。旧 PID 已被无关系统进程复用，检查命令行后没有结束该进程。重新运行读者后真实数据正常解析，并观察到序号和时间连续增长。

用户问为什么耗时：这次是诊断旧读者退出、重放约 10 MB 日志、再等待采样确认。不是一次 AI 问答必须固定等待数分钟。启动重放全部历史确实是当前实现待改善的问题。

GitHub 操作曾受工具能力限制：连接器有登录但未提供创建仓库动作；本机有 Git、无 gh 登录。随后从 GitHub CLI 官方发行版安装便携 gh，用户完成设备登录，成功创建并推送私有仓库。不要再让用户重复建仓库。另一台电脑是否已登录仍需现场核实。

## 仓库和代码位置

- 仓库：[polopineapplem/wow-context-bridge](https://github.com/polopineapplem/wow-context-bridge)，默认分支 main。
- 已安装插件：游戏目录的 `Interface\AddOns\LocalContext`。

仓库 checkout、正在运行的读者和游戏里装的插件不会自动同步。改了仓库源码后，要核对实际运行的读者路径和安装的插件版本（`check-setup.bat` 会检查插件版本）。不要照搬别的电脑上的绝对路径。
